# Jazz-Inador

Final data science project. It filters music in real time within a shared playback queue, classifying the genre of recommended songs with a CNN (convolutional neural network) or Random Forest model. If a recommended song is not of the selected genre (JAZZ), it is not played and is skipped in the playback queue.

## Framing

**The problem.** A jazz club wants its guests to suggest songs in real time into one shared playback queue, as long as
the songs are jazz. Today someone on staff would have to listen to every suggestion and decide. Jazz has no clear rules
(swing, bebop, modal, fusion, bossa-adjacent...), so a fixed list of artists or keywords doesn't work either.

**Who it matters to.** The club, which keeps control of the music without a person screening the queue, and its guests,
whose suggestions get an answer in seconds.

**The decision.** For every song a guest adds to the club's YouTube Music playlist: **keep it** (it will play) or
**remove it** (it never plays). The model's output is used only for that decision; nothing else is automated.

**The metric and the cost of each error.**

| Error | What happens in the club | Cost |
|---|---|---|
| **False positive**: a non-jazz song is kept | It plays and breaks the mood of the room, with no one to stop it | **High**: this is the main risk named in the proposal |
| **False negative**: a jazz song is removed | A guest's suggestion silently disappears | Lower: the club still only plays jazz, but a guest is annoyed and may stop using the feature |

Because false positives are the expensive error, the metric that matters is **precision of the kept songs** (of the
songs the filter lets through, how many are jazz), reported together with the **false-pass rate** (share of non-jazz
songs let through), which unlike precision doesn't depend on how many suggestions are jazz. **Jazz recall** (share of
jazz songs kept) is the secondary metric: if it is too low guests stop trusting the system.

**The rule.** A song is kept only if *jazz* is the most likely of the 10 genres, averaging the CNN's probabilities over
its 3-second segments. The CNN was chosen over the random forest **before** looking at the test set, from validation
accuracy and the 73 external jazz recordings ([cnn/cnn_vs_random_forest.ipynb](cnn/cnn_vs_random_forest.ipynb)).

**Results with that rule (CNN, song level, test set touched once):**

| Metric | Value | 95% interval (Wilson) |
|---|---|---|
| Precision of kept songs (holdout, 20 jazz + 180 other songs) | 18 / 21 = 85.7% | 65% – 95% |
| False-pass rate (non-jazz songs kept) | 3 / 180 = 1.7% | 1% – 5% |
| Jazz recall (holdout) | 18 / 20 = 90% | 70% – 97% |
| Jazz recall on 73 external jazz recordings | 62 / 73 = 84.9% | 75% – 91% |

The holdout has only 10% jazz, which makes its precision pessimistic for a jazz club, where most suggestions should be
jazz. With the same recall and false-pass rate, precision would be about 98% if half of the suggestions were jazz and
99.5% if 80% were. Those figures are a projection, not a measurement: we have no data on what guests actually suggest.

## Data

[GTZAN](https://www.kaggle.com/datasets/andradaolteanu/gtzan-dataset-music-genre-classification/data?select=Data):
1,000 clips of 30 seconds, 10 genres × 100, recorded by Tzanetakis & Cook around 2000–2001. We only use the raw audio
(`genres_original`); spectrograms and features are generated by the scripts in [data_generator/](data_generator/), with
the same code the live filter uses on new songs. The proposal planned to use a Kaggle dataset of pre-computed mel
spectrograms; we switched to GTZAN's raw audio so training spectrograms and live spectrograms come from the same
pipeline.

Provenance, cleaning and the findings that changed the project's decisions are in
[data_generator/eda.ipynb](data_generator/eda.ipynb).

## Commands

####  Install dependencies:

```bash
uv sync
# Optional: also install PyTorch (CUDA) to train the CNN on an NVIDIA GPU.
# Not needed to use the trained models.
uv sync --group gpu
```
#### Generate data

```bash
# Generate spectrograms:
uv run data_generator/wav_to_mel_spectrograms.py
# Generate features CSV:
uv run data_generator/features_to_csv.py
# Validate data:
uv run data_generator/validate_dataset.py
```
#### Train models
```bash
# Train random forest
uv run random_forest/random_forest_genres.py
# Train CNN (NumPy, CPU)
uv run cnn/cnn_genres.py
# Train CNN (PyTorch, NVIDIA GPU with CUDA 13; needs uv sync --group gpu)
uv run --group gpu cnn/cnn_genres_torch.py
```

#### Classify audio files using each model

```bash
# Classify an audio file with the random forest:
uv run random_forest/random_forest_genres_classifier.py <audio_file>
# Classify an audio file with the CNN (models/cnn.json):
uv run cnn/cnn_genres_classifier.py <audio_file>
```

#### Evaluate both models on external jazz recordings

```bash
# Put the audio files in test/jazz/, then:
uv run test/evaluate_external.py
```

#### Run the live playlist filter

Needs [deno](https://deno.com) on the `PATH` (YouTube's download challenge is solved with it; without it, some
downloads fail with HTTP 403) and a login to the YouTube Music account that owns the playlist.

```bash
# Once: install the filter's dependencies and deno
uv sync --group playlist
curl -fsSL https://deno.land/install.sh | sh

# Once: log in. Paste the request headers of a music.youtube.com "browse" request (browser DevTools > Network).
# browser.json is the account's session: never commit or share it (it is in .gitignore).
uv run --group playlist ytmusicapi browser --file playlist_filter/browser.json

# Try it: classify and log, never remove anything (works on any public playlist without logging in)
uv run --group playlist playlist_filter/playlist_filter.py --playlist <playlist id> --dry-run --once

# Run it: checks the playlist every 10 s and removes the songs that are not jazz
uv run --group playlist playlist_filter/playlist_filter.py --playlist <playlist id> --workers 2
```

The playlist id is the part after `list=` in the playlist's URL. Decisions are logged to `playlist_filter/log.txt`
and remembered in `playlist_filter/state.json`; delete that file to start fresh (for example after a dry run, whose
"would remove" songs are otherwise skipped).

## Deployment and limits

### How it is used

1. The club creates a collaborative YouTube Music playlist and shares the link with its guests (QR code at the bar).
2. A computer at the club runs [playlist_filter.py](playlist_filter/playlist_filter.py), logged in as the playlist's
   owner. Every 10 seconds it reads the playlist and takes every song it hasn't seen yet.
3. For each new song it downloads the audio, cuts 6 clips of 15 seconds spread across the song, classifies their
   3-second segments with the CNN and averages the probabilities. If jazz is the top genre the song stays; otherwise
   it is removed from the playlist before it plays.
4. Several songs are processed in parallel (`--workers`). A song gets its decision about 10–15 s after the filter sees
   it on a fast laptop; on a slower one, songs added in bulk queue at about one decision every 7 s.

Classifying 6 clips instead of the whole song is about 10× faster. On 18 test songs it gave the same keep/remove
decision as classifying the whole song every time; that is a small check, not a proof.

### What we would monitor

| Signal | Why | Source |
|---|---|---|
| Share of suggestions removed per night | A sudden rise or drop means the guests' music changed or the model drifted | `log.txt` |
| Distribution of the jazz probability of kept songs, and share of decisions near the boundary | Drift: new styles the model has never heard pile up near the decision boundary | `state.json` |
| Songs re-added after being removed | Guests disagreeing with the filter: likely false negatives | playlist + `state.json` |
| Non-jazz songs the staff hear playing | False positives, the expensive error; each one becomes a labeled example for retraining | staff notes |
| Download / classification errors and their retries | HTTP 403 (YouTube's download challenge), an expired login, YouTube changing its site | `log.txt` |
| Time from a song being added to its decision | A song added right before it plays may start before the filter removes it | `log.txt` |

### What this work does NOT let us conclude

- **That the filter recognizes "jazz" in general.** It recognizes which of GTZAN's 10 genres a song sounds most like.
  Anything outside those 10 is forced into one of them: bossa nova came out as *country* (Chega de Saudade) and *blues*
  (The Girl from Ipanema), as the proposal predicted. Fusion, smooth jazz, lo-fi, soundtracks and Latin jazz are
  untested.
- **Whether a song fits the mood of the night.** A chaotic free-jazz track is still jazz to the model.
- **Its precision on real suggestions.** The holdout has only 20 jazz songs (intervals of ±15 points), and the 73
  external recordings are all jazz: they measure recall, not precision. We have no external set of non-jazz songs,
  and no data on what guests actually suggest.
- **That the holdout results carry over to new music.** GTZAN is from 2000–2001, has several clips by the same artist
  and known labeling errors. It also has 14 pairs of byte-identical clips (found in the EDA, after training): 6 of the
  200 test songs have an identical copy in training, which inflates song accuracy by up to 2.5 points (none of them is
  jazz). We split by song, not by artist, so the model may have heard the same artist in training and test: the
  holdout numbers are probably optimistic.
- **That the live filter scores exactly what we evaluated.** The evaluation classifies whole songs; the live filter
  classifies 6 clips per song. They agreed on 18 of 18 test songs, a small sample.
- **That it works with real users.** It was tested on playlists filled by the team, not in a club with guests.

**Operational limits.** It removes songs from the playlist; it doesn't skip a song that is already playing. It needs
the computer on and connected the whole night. It uses an unofficial YouTube Music API (`ytmusicapi`) and a browser
login that expires, so YouTube changing its site or the session expiring stops the removals until someone fixes it.
